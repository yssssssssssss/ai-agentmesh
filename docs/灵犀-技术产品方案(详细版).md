# 灵犀 Lingxi · 技术产品方案(详细技术版)

> 定位:以「员工数字分身」为核心、以「分身间自主通信(A2A)」为骨架的组织级 AI 协同平台。
> 配图:`灵犀-顶层架构图.png`、`灵犀-运行时执行流图.png`。
> 工程纪律:单一技术栈(TypeScript / Express / PostgreSQL / React)、单一事实源(PostgreSQL)、无重型 Agent 框架(不引入 LangGraph / CrewAI / 独立消息队列 / 独立向量库)。

---

## 1. 总体架构(见「顶层架构图」)

灵犀自上而下由七层构成,核心是把"员工—分身—能力—记忆"用一条**可治理、可回放的通信骨架(A2A)**串起来:

1. **接入层**:Web 工作台(React)+ 实时协同通道(`ws` WebSocket,挂载于同一 HTTP Server)。
2. **数字分身层**:每位员工一个分身运行时,负责意图规划、能力编排,并通过 **A2A 协同总线**与其他分身通信。
3. **通用能力层(能力市场)**:检索 / 数据 / 生成 / 会议 / 风险 / 记忆六类能力,注册 + 授权后由分身调用。
4. **项目上下文层**:一切工作绑定 `design_project`,进时间线、带来源。
5. **三级记忆层**:个人 / 项目 / 团队记忆,经候选确认形成飞轮。
6. **治理与安全层**:人审 Inbox、风险四信号、能力授权、全程审计——贯穿所有分身行为。
7. **数据与外部层**:PostgreSQL 单一事实源,外接 LLM、实时 ASR、只读连接器。

三条工程纪律保证系统可控:**单一技术栈**降低维护与交付成本;**单一事实源**让所有分身/协同状态落库、可回放、可审计;**无重型框架**使自主性由清晰、可测试的领域服务实现,而非黑盒编排——这也是通过企业安全合规的前提。

## 2. 数字分身运行时(DigitalTwin Runtime)

### 2.1 分身 = 身份 + 画像 + 记忆 + 授权

分身不是新造用户,而是绑定既有 `users` 的运行时聚合:身份/权限继承员工本人(权限不超过本人);画像来自行为画像快照(注入 system persona);人格来自个人长期记忆,工作内存来自会话短期记忆;可调用能力由授权表决定。

### 2.2 数据模型

```text
digital_twins        id, user_id(唯一), status, persona_summary,
                     profile_snapshot_id, autonomy_level, config, ...
twin_runs            id, twin_id, design_project_id, trigger(user/a2a/schedule),
                     intent, status(queued/running/completed/failed/needs_review),
                     capability_calls[jsonb], outputs[jsonb], error, created_by, ...
```

### 2.3 落盘式自主运行时(关键技术点)

分身的每一次执行都是一条 `twin_runs` 记录,遵循 `INSERT → setImmediate 后台执行 → 写回` 的落盘异步范式(复用 DesignOS 已验证的 `tool_runs` / `ai_jobs` 模式)。由此获得三个工程特性:**可回放**(执行轨迹与能力调用全部入库)、**跨实例**(任意实例可查询/接续)、**重启存活**(进程重启不丢状态)。这刻意不使用内存队列或独立消息中间件,避免引入不可审计的黑盒运行时。

### 2.4 自主级别(autonomy_level)

- `manual`:仅按用户显式指令执行。
- `assisted`(默认):分身可自主规划并调用**只读/低危**能力,但产出一律为**候选**。
- `autonomous`:在风险规则齐备且灰度开启后,允许自主发起外部检索与 A2A 协同;高影响动作仍回流人审。

`autonomy_level` 是贯穿运行时与通信的总闸门,决定分身"能自主到哪一步"。

---

## 3. 通用能力层与授权闸门

能力先注册、再授权:`ai_capabilities`(name / category / provider / risk_level / autonomy_allowed / enabled)登记能力,`twin_capability_grants`(按角色或单分身)控制可调用范围。分身执行任一能力前,依次校验:**分身身份 → 角色/分身授权 → 能力 autonomy_allowed × 分身 autonomy_level → 风险四信号**;任一不过则阻断或转人审。高危能力(批量外部调用、跨项目访问、写团队记忆、外部写操作)默认对普通分身关闭。外部连接器 V1 只读,结果一律归一化为 `sources` 并落 `connector_runs`。

## 4. Agent 沟通能力:A2A 协同协议(核心)

灵犀区别于"单体 AI 助手"的本质,在于分身之间能像同事一样**自主通信、分派与交接**。这套能力称为 **A2A(Agent-to-Agent)协同协议**,是系统的骨架。

### 4.1 设计目标

让多个分身在**同一项目上下文**内,无需人拉群开会,即可自主完成"请求—取证—交接—提案"的协作闭环;同时保证**每一次通信都绑定项目、可回放、可审计,且产物不越权**。

### 4.2 消息模型

```text
a2a_messages
  id
  design_project_id     -- 协同必须绑定项目上下文,天然可追溯
  from_twin_id
  to_twin_id            -- 可空:为空表示广播给项目内相关分身
  msg_type              -- request / evidence / handoff / decision_proposal / risk / ack
  ref_type, ref_id      -- 关联对象:requirement / meeting / source / candidate / twin_run
  payload               -- jsonb:结构化内容(非自由文本,便于机器消费与回放)
  status                -- open / accepted / done / rejected / needs_review
  created_at, updated_at
```

### 4.3 消息类型语义(协议词汇表)

- **request(请求)**:分身向另一分身或广播发起协作请求(如"需要竞品与上线指标支撑")。
- **evidence(证据)**:回传取证结果,内容已归一化为 `sources`(带引用,不可伪造)。
- **handoff(交接)**:把一段工作连同上下文移交给下一能力/分身(如把证据交给"生成能力"产出草案),并在 `activity_logs` 留痕。
- **decision_proposal(决策提案)**:提出结论,但仅作为**候选记忆**提交,需人确认后才生效。
- **risk(风险提示)**:标记风险信号,触发风险审核并可生成 review-item。
- **ack(回执)**:确认接收/完成,驱动协同状态机流转。

消息体是**结构化 payload 而非自由文本**,这让协同可被机器消费、聚合、回放,而不是又一条聊天记录。

### 4.4 传输机制:落盘异步的 a2aBus(关键技术点)

分身通信不走内存事件总线,而走**落盘异步**:

```text
分身A 产生消息 → INSERT a2a_messages(status=open)
             → setImmediate 投递给目标分身运行时(twinRuntimeService)
             → 目标分身处理 → 写回 status=accepted/done
```

由此,**每一条分身间消息都是数据库中的一等公民**:可查询、可回放、可审计、跨实例可见、重启不丢。可选一个默认关闭的后台 worker 处理广播扇出与超时重投(仿 auto-post drain 模式,`enabled=false` 默认)。**绝不引入独立消息队列基础设施**——这是"可审计"与"工程可控"的关键取舍。

### 4.5 寻址与协同会话

- **点对点**:`to_twin_id` 指定目标分身;**广播**:`to_twin_id` 为空,投递给项目内相关分身(按角色/参与度路由)。
- **协同会话状态**:围绕一个任务的多轮 A2A 交互,用**增量归约**维护协同状态(参考会议模块的 `meetingState` reducer),不把全量历史反复塞给模型——既省 token,又让状态可解释、可回放。

### 4.6 通信的护栏(自主 ≠ 越权)

A2A 的自主性被四层护栏约束,保证"主动而不越权":

1. **绑定项目**:所有消息挂 `design_project_id`,进项目时间线。
2. **产物即候选**:协同得出的任何结论(decision_proposal)都是候选,须经人确认才成为项目/团队事实。
3. **高危自动升级**:跨项目访问、批量外部调用、写团队记忆等消息,自动触发风险四信号并进人审。
4. **受 autonomy_level 约束**:仅当分身处于 `autonomous` 且能力 `autonomy_allowed=true` 时,才允许自主发起对外协同;否则回落为"建议人确认后发起"。

### 4.7 与既有工程的一致性

A2A 是对 AgentMesh 黑板(request/evidence/decision/handoff/archive)思想的**协议化落地**,但**不新建平行 BBS 界面**:evidence→`sources`,risk→风险评估/review-item,decision→候选记忆,handoff→`activity_logs`+review-item。它复用 DesignOS 的项目上下文、时间线与审计,把"多 Agent 通信"这件事牢牢锁在可信底座内。

## 5. 运行时执行流(见「运行时执行流图」)

### 5.1 分身运行时主流程

`触发(用户下达 / 收到 A2A 消息)` → `检索分层记忆(会话·项目·个人·团队)` → `意图规划(受 autonomy_level 约束)` → `能力调用·闸门(授权检查 + 风险四信号)`；通过则执行(记 `tool_run`/`ai_job`/`connector_run`),命中风险或越权则**阻断并转人审** → `结果归一化为来源(sources)` → `产出候选 + 写会话短期记忆` → `高影响结论进人审 Inbox` → `确认后沉淀三级记忆 + 全程审计(可回放)`。

### 5.2 分身间通信子流程(A2A)

`分身A 发 request` → `a2aBus 落盘(a2a_messages, open)` → `setImmediate 投递` → `分身B 接收→取证/执行` → `回 evidence / handoff(归一化来源)` → `decision 候选 → 人确认沉淀`。全程绑定项目、进时间线、可回放。

---

## 6. 三级记忆与分层检索

记忆表不变(`user_memories` / `project_memories` / `team_memories` + `chat_session_memories` + 各候选表)。检索时 `memoryRetriever` 按"**会话短期 → 项目已确认决策/风险 → 个人偏好 → 团队规范 → 相关工具/会议结论**"的分层顺序为分身组织上下文;写入时,分身只能自动写会话记忆、按 `writePolicy=auto && confidence≥0.6` 写低危个人偏好,其余走候选。团队记忆必须负责人确认。记忆元数据 `source_kind` 增加 `twin`,`source_event_id` 关联 `twin_runs`/`a2a_messages`,使"哪个分身、在哪次协同里提出"可回查。

---

## 7. 可信治理引擎

任何分身产出都经五步可信流水线:`绑定来源(sources,引用不可伪造)` → `风险四信号(注入/来源策略/高危工具/需人批准)` → `人审 Inbox(候选表只读 UNION)` → `确认沉淀` → `全程审计(activity_logs + memory_events + twin_runs + a2a_messages)`。三条红线不可逾越:AI 产出不作为事实源、团队记忆必须人审、外部连接器只读。

---

## 8. 数据模型汇总

新增:`digital_twins`、`twin_runs`、`ai_capabilities`、`twin_capability_grants`、`a2a_messages`、`risk_policy_rules`、`risk_assessments`;记忆元数据 `source_kind` 增加 `twin`。复用:`users` / `person_profile_snapshots` / 三级记忆表 / 候选表 / `sources` / `artifact_sources` / `tool_runs` / `ai_jobs` / `activity_logs` / `memory_events` / `design_projects`。

---

## 9. 非目标(明确不做)

不把产品做成 chat-first 命令行;不搬 AgentMesh 的实现代码、单文件前端、完整 BBS 页面;不引入重型 Agent 框架、独立消息队列、独立向量库;不让分身在 `autonomy_level` 未开启时自主对外通信或写任何正式记忆。
