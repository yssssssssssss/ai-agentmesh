# 协作图：让 Agent 协作可被看见

> 面向投资人与合作伙伴的产品材料。版本：2026-07-12。
> 产品范围：AgentMesh 协作图的两个可解释视图——**协作流程图**与**项目时间线**，以及支撑它们的协作黑板 BBS 事件账本、任务模型与治理能力。

---

## 1. 一句话定位

**协作图把黑箱的多 Agent 协作，变成一眼看懂的"任务地图 + 时间线"：谁发起、谁在做、卡在谁、证据从哪来、下一步谁接手，全部可读、可查、可追溯。**

它不是流程图美化工具，也不是把 Agent 对话堆进一个界面。协作图的每一个节点、每一条连线，都直接映射到底层被结构化记录的协作事件。可视化之所以成立，是因为协作过程本身已经被 AgentMesh 沉淀为可回放的证据账本——这正是竞品的群聊记录和运行日志给不出的东西。

对外可包装为：**企业 Agent 协作的可解释层（Explainability Layer）**。谁都能接模型、编排 Agent，但很少有人能把"这群 Agent 到底做了什么、结果可不可信"讲清楚给管理者、业务负责人和合规人员看。

---

## 2. 要解决的问题

企业把多个 AI Agent 接入工作流之后，第一个撞上的墙不是能力，而是**不可见**。

| 现状 | 造成的业务损失 |
| --- | --- |
| 多 Agent 协作是黑箱，只看到最终输出 | 不知道谁在做、卡在哪一步、能否恢复，出问题无法定位 |
| Agent 之间的信息传递散落在日志或群聊里 | 无法回答"这个结论的证据从哪来、谁负责"，结果不敢进正式流程 |
| 任务在多个 Agent 间流转，责任边界模糊 | 交接时上下文丢失，下一个 Agent 从零开始 |
| 管理者、业务方、合规方各自需要不同视角 | 没有统一的可解释视图，每次追溯都要翻原始记录 |

协作图要回答的，正是负责人每天在问的四个问题：**任务由谁发起？当前卡在谁？证据从哪里来？下一步由谁接手？**

---

## 3. 产品定义：两个可解释视图

### 3.1 协作流程图 —— 时间列对齐的泳道图

- **横轴是统一时间刻度**：所有 Agent 的动作按真实发生顺序排到同一条时间轴的列上，一个动作占一列。
- **纵轴是 Agent 泳道**：每个参与的 Agent 占一行，它的动作落在自己那一行、对应的时间列上。
- **两类关系用两种线区分**：
  - **回复 / 推进**（实线）：一个动作在回应或推进另一个动作（如 evidence 回应 request）。因为时间恒向右推进，这类线**永远从左到右**，不会倒流。
  - **任务交接 handoff**（虚线）：一个 Agent 把任务正式交给下一个负责人。虚线独立走线，和回复实线在几何上分离。
- 连线采用**正交折线（直角走线）**，像流程图/地铁图一样只走水平段和垂直段，绝不斜穿——彻底消除了曲线斜拉造成的"意面式"交叉。

一眼看懂：谁先发起 → 谁补了证据 → 谁提示了风险 → 谁做了决策 → 交接给了谁。

### 3.2 项目时间线 —— 每项目一条独立竖轴

- **按项目分组**：每个协作任务一张独立卡片，卡内是该任务**自己的**紧凑竖向时间线，只含这个任务的事件。
- **卡头给出全景**：任务标题、状态徽章、时间跨度（如"18:05–18:09 · 4 帖"）。
- **卡内逐条可读**：左侧真实时刻、彩色轴点串成一条线、右侧事件气泡（Agent 头像 + 名称 + 事件类型 + 内容）。

项目之间互不干扰，不会因为把所有事件塞进一条全局竖轴而产生巨大空白间隔——顺着一张卡片读下来，就是这个项目的完整来龙去脉。

## 4. 技术实现

协作图的可信，来自"上层可视化"与"底层协议"的严丝合缝。

### 4.1 底层协作协议：结构化事件账本

协作图不是从聊天记录里"猜"出来的，而是直接渲染底层的 `BlackboardPost` 事件。系统支持 **9 种结构化事件类型**（`agentmesh/models.py:59-68`）：

| 事件类型 | 含义 |
| --- | --- |
| `request` | 提出需要补充的信息或行动 |
| `evidence` | 服务 Agent 或内部能力返回的**带来源**证据 |
| `risk` | 风险策略命中的结论 |
| `decision` | 任务决策 |
| `handoff` | 结构化交接包 |
| `digest` / `archive` | 摘要与归档 |
| `correction` | 对既有结论的纠正 |
| `memory_candidate` | 可提升为团队记忆的候选 |

**因果链是可视化的骨架**：
- 每条帖子可带 `related_post_id`，把 evidence / risk 回链到它响应的 request（前端据此画**回复实线**）。
- 交接事件携带 `StructuredHandoffPacket`（`models.py:322-328`），其中 `next_owner_agent_id` 指向下一负责人，还包含 `goal`、`current_result`、`done_when`、`blockers`、`requires_input_from`（前端据此画**交接虚线**并更新任务归属）。

这些事件由 research / data / risk 三类服务 Agent 在授权范围内写入：个人 Agent 知识不足时创建 request；research/data 取证后以 evidence 回帖并回链 request；risk Agent 命中风险时写 risk 帖（`agentmesh/agents.py`、`agentmesh/routes/blackboard.py`）。

### 4.2 前端可视化引擎

| 技术点 | 实现 |
| --- | --- |
| **时间列对齐** | CSS Grid 模板 `158px repeat(N, minmax(132px,1fr))`——一帖一列（时间列），Agent 映射到 `grid-row`（每 Agent 一行），从布局层保证同列即同刻 |
| **正交折线路由** | `orthoPath` 算法用 `L`（直线段）+ `Q`（二次贝塞尔圆角，R=7）拼接，只走直角；回复线走"源右缘 → 列间垂直通道 → 目标左缘"，交接线走"源边 → 行间水平通道 → 目标边"，两者几何正交、互不缠绕 |
| **线型语义** | `flow-link` 实线 = 回复/推进，`handoff-link` 虚线 = 交接；多条线的通道按序错开，避免重叠 |
| **渲染健壮性** | 连线依赖节点真实几何位置（`getBoundingClientRect`），用 `requestAnimationFrame` + 120ms `setTimeout` 双触发兜底，解决从隐藏态切入时布局未稳定导致的连线丢失 |
| **项目时间线** | 按 `task_id` 分组，项目顺序优先跟随任务卡；每项目渲染为独立竖轴卡片 |

（前端实现见 `app.html` 的 `renderGraphFlow`、`drawFlowLinks`、`renderGraphTimeline`。）

### 4.3 为什么这是壁垒

单独看，"画一张泳道图"不难。难的是：**图上每个节点都对应一个带来源、带责任人、带时间、带因果关系的结构化事件，而不是一段无法追溯的文本。**

- 竞品若只有 Agent 群聊或运行日志，可视化只能停留在"消息流"层面——画得出顺序，画不出"证据回链"和"责任交接"。
- AgentMesh 的可视化能成立，前提是底层已经把协作强约束为事件账本（任务、证据来源、执行锁、结构化交接）。这套协议 + 治理 + 可视化协同工作的能力，需要长期工程沉淀，不是套个图表库能复制的。

## 5. 市场优势

**可解释性正在从"锦上添花"变成企业 Agent 采购的刚需。** 当企业把 Agent 放进真实业务流程，三类角色立刻需要看懂协作过程：

- **管理者**：需要快速定位"任务卡在哪、谁在等谁"，而不是等最终结果超时才发现。
- **合规 / 审计**：需要追溯"这个进入正式流程的结论，证据从哪来、经过谁、是否做过风险检查"。
- **业务负责人**：需要复核过程本身，判断能否信任这次自动化的产出。

协作图直接服务这三类角色。它把"Agent 到底做了什么"从工程师的日志里，翻译成业务方和管理者能读的地图与时间线。这是从"能跑"到"敢用"的关键一跃。

## 6. 竞争对比

市场已经证明企业愿意为 Agent 编排、治理和跨系统连接付费：Microsoft Copilot Studio 已将 connected agents、handoff 和 guardrails 写入多 Agent 编排指南；Salesforce Agentforce 强调在统一平台中编排 Agent、工具、数据和治理；ServiceNow 把 AI Agent Orchestrator 定位为跨团队 Agent 协作的控制台；Glean 提供面向企业上下文的 workflow 与 autonomous agent builder。

| 产品类别 | 代表产品 | 已验证强项 | 在"协作过程可解释"上的差距 / AgentMesh 的切入 |
| --- | --- | --- | --- |
| 企业搜索与工作 Agent | Glean | 企业上下文、权限继承、无代码 Agent 与工作流 | 强于"找到答案"，弱于"解释这群 Agent 如何协作产出答案"；AgentMesh 把证据链、交接、责任转移做成可视对象 |
| 办公套件 Agent 平台 | Microsoft Copilot Studio | M365 集成、connected agents、生成式编排 | 编排能力强，但过程呈现偏配置视角；AgentMesh 提供面向业务方的任务地图与时间线 |
| CRM Agent 平台 | Salesforce Agentforce | Customer 360 数据、流程、MCP/A2A、可观测性 | 可观测性面向运维；AgentMesh 的可解释视图面向管理者、业务与合规 |
| IT 服务管理 Agent | ServiceNow AI Agents | ITSM 工作流、跨部门编排、中央治理 | 聚焦 ITSM 流程；AgentMesh 服务设计、产品、研发等知识密集协作的过程解释 |
| Agent 构建器 | Dify | 可视化工作流、模型/工具编排、私有化 | 画的是"预先设计的流程图"；AgentMesh 画的是"运行时真实发生的协作事件" |

**关键判断**：不与上述平台正面争夺通用 Agent builder 市场。协作图的定位是成为企业内部现有模型、工具、数据源和 Agent 平台之上的**可信协作可解释层**——运行时真实发生的协作，被记录、被解释、被治理。

## 7. 核心竞争优势

1. **可视化直连结构化事件账本**：图上每个节点都对应一个带来源、责任人、时间、因果的 `BlackboardPost`，而非无法追溯的消息。
2. **两类关系清晰分离**：回复/推进（实线）与任务交接（虚线）在语义和几何上都区分，正交折线消除交叉，负责人不必费力解读。
3. **两种视角互补**：协作流程图看"结构与责任"，项目时间线看"节奏与顺序"，覆盖不同角色的阅读需求。
4. **证据优先、风险内建**：工具结果成为带来源的证据，可疑外部内容在进入模型合成前被隔离——可视化上呈现的是可信的协作，而非无法复核的文本。
5. **护城河在协同机制**：任务协议、权限、证据、风险、人审、记忆治理一起工作，可视化只是它们的出口。单点图表易仿，这套运行机制需长期沉淀。

## 8. 能力边界与红线（诚实披露）

为保证材料可信，明确区分"已实现可演示"与"产品路线待做"。

| 已可演示 | 尚待产品化 |
| --- | --- |
| 任务、BBS 帖、证据来源、风险隔离、人工审核、执行锁、结构化交接、协作流程图、项目时间线、仅 research 的自动派发闭环 | 通用任务 DAG、跨实例可靠队列、自动重试、Agent 自主计划、通用 handoff 自动消费、生产级关系模型 |
| research / data / risk 三类服务 Agent，可配置 Web / O2 / HTTP 接入边界 | 经真实企业数据与长期负载验证的生产连接器（当前 research 默认 Mock、data 回落样例、O2 需宿主机 CLI） |
| 单页应用中的完整可视化与交互 | 前端从单文件 `app.html` 迁移到组件化；存储从单表 KV 迁移到生产级关系模型 |

**三条产品红线**：AI 产出不是事实源；团队记忆不自动接受；外部连接器默认只读，写操作与高风险行为进入审批。

（后端能力与治理由 `tests/test_chat_flow.py` 覆盖：任务派发、风险隔离、执行锁、结构化交接、证据→记忆候选、BBS API 等，项目自述 220 项测试。）

## 9. 商业化路径

先从**跨角色协作频繁、信息来源复杂、结果必须可追溯**的团队切入：设计与产品、研发效能与技术支持、运营与策略、企业研究与数据分析。

1. **试点闭环**：接入真实只读数据/检索连接器，以协作图为验收看板，度量来源覆盖率、人工介入率、任务时长、记忆接受率。
2. **部门订阅 / 私有化**：围绕授权、连接器、审计和项目记忆部署。
3. **企业协作可解释底座**：对接既有知识库、数据平台与 Agent 平台，按活跃席位、受管能力、协作任务量组合计费。

**投资叙事**：企业 Agent 已进入采购期，但"协作过程可解释、结果可追溯"仍是被低估的基础设施层。协作图是这一层最直观的入口。

---

## 10. 路演口播提纲

- **开场**：企业不缺会干活的 Agent，缺的是"看得懂这群 Agent 干了什么"。多 Agent 协作今天基本是黑箱。
- **产品**：协作图用两个视图解开黑箱——协作流程图看结构与责任，项目时间线看节奏与顺序。
- **演示**：一个需求进来，个人 Agent 发现知识不足发起 request，research_agent 回传带来源 evidence，risk_agent 检查风险，随后交接给组长。协作图上，这条链路的每一步、每一条实线（回复）和虚线（交接）都清清楚楚。
- **技术**：图上每个节点都是底层结构化事件，带来源、责任人、时间和因果——这不是画图，是把可追溯的协作账本翻译给人看。
- **差异**：大平台擅长编排与既有数据域，协作过程呈现偏工程视角。我们把它翻译成管理者、业务、合规都能读的地图。
- **愿景**：让每一次 Agent 协作都被看见、被信任、被复用。
